# 领域说明

公司行动会改变证券数量、现金、成本和可售状态。业务记录通常同时包含公告版本、除权日、登记日、到账日和更正时间，核算时应区分事件发生顺序与数据到达顺序。持仓批次、币种精度、碎股处置和冻结数量属于需要长期保存的领域信息。

`reference/domain.json` 保存可公开的示例枚举与精度约定。正式业务记录应使用稳定标识，并区分业务发生时间、系统接收时间和记录版本。

`reference/sample_data.json` 是投诉案例的完整样例：同一只股票接连发生拆股、配股、现金红利再投资与跨账户转入，随后红利公告与汇率迟到更正。

## 核算模型

### 事件溯源与版本

- `events.jsonl` 只追加，是系统唯一事实来源；任何核算状态都可由它全量重放推导。
- 每次 `POST /rebuild` 全量重放并产生一个新的**核算版本**（version 单调递增，带 `version_hash`/`state_hash`）。
- **迟到事件只产生新版本**：已出具的客户快照（snapshot）永不改写，快照记录其所属版本号与哈希。
- 重放在内存中一次算完，先写临时文件再原子替换并推进 `current` 指针；**重算失败不留半套结果**，当前版本保持不变。

### 真实业务顺序

步骤按 `(生效日, 阶段, 业务标识, 公告版本, 接收序号)` 排序，与消息到达顺序无关。同日阶段序：

1. 现金存入/支取；
2. 跨账户转入（持仓基数先到位）；
3. 拆股（先调整数量与单位成本）；
4. 成交（登记日按日终持仓确定权益）；
5. 配股/红利权益登记；
6. 配股缴款到账、红利到账、红利再投资；
7. 跨账户转出（最后执行，避免漏算转出方权益）。

到账日落在非交易日时按市场日历顺延（FOLLOWING）。

### 公告版本、更正与撤销

- 公司行动按 `action_id` 归并，**最高 `announcement_version` 生效**，旧版本记入 `superseded_actions`。
- `status: cancelled` 的公告整体作废，记入 `cancelled_actions`，不产生任何步骤。
- 同一 `action_id + announcement_version` 内容不一致的重传会被拒绝，必须提高版本号走更正流程。

### 幂等

- 同一 `message_id` 重传：返回首次处理结果，不产生副作用。
- 同一业务标识（成交号、划转号、公告号+版本、汇率键、入金号）内容一致的重传同样幂等；内容冲突则拒绝。

### 明确去向

- **碎股**：配股/拆股不足一股的部分按公告价折现（`cash_in_lieu`）或作废，现金流水与备注逐笔可查。
- **现金选择权**：账户层 `election` 选择 `cash` 时，配股权益按折现价兑现，不产生新批次。
- **冻结数量**：未确认的转出按 FIFO 冻结到具体批次，冻结台账随拆股同比例缩放；确认后解冻并扣减。冻结部分不可卖出。
- **跨币种费用**：费用按到账日（或此前最近可得日）汇率折算为持仓币种，认购费用资本化进新批次成本，红利费用从现金扣减；每次换算记录 `fx_usages`（汇率、取值日、来源版本、用途），汇兑损益由此可解释。

### 成本沿革与校验

- 每个批次记录 `root_id`（谱系根）、`derived_from`（派生来源）与逐笔 `history`；任一持仓日的总额可分解到原始批次。
- `GET /export/lineage` 导出含完整版本文档的成本沿革；`POST /verify` 独立重算 `state_hash` 与 `version_hash` 并抽查谱系总额，可检测篡改。
